# Decision · 打包范围（Q4）

日期 2026-11-19。用户批复：「技能/mcp/文档/知识库/从属角色所有文件都要打包」。

## 判读（假设，允许用户纠正）

原句最自然断句为「从属**于**角色**的**所有文件」——所列类别即角色的从属内容，**不需要角色层级机制**。据此：

- **技能**：`skills.roles[skillId]` 含该角色的技能（专属），整目录打包（SKILL.md + 参考文档/脚本——「文档」若指技能附带文档，已天然覆盖）。
- **MCP**：`mcp.roles[mcpId]` 含该角色的 MCP，配置 + **解密后的秘密值**一并进包（用户明示「所有文件都要打包」；包内秘密为明文属固有风险，导入侧重加密回 secrets.json，UI 提示一次性）。角色共享（roles 含多个角色）的技能/MCP 同样进包——它是该角色能力的一部分；导入后 ext-roles 置为仅新角色。
- **知识库**：`~/.deva/personas/knowledge/<id>/` 整目录打包（issue#65 档 0 约定，用户自用形态）。
- **文档**：无独立实体；知识库目录与技能目录里的文档随整目录打包，不单列机制。
- **从属角色**：按「从属内容」判读，不建角色层级/引用探测机制。若用户实意是「打包其他角色」（递归子角色），此决策作废重议——已在 open-questions 留纠正窗口。

## 导入侧联动

- 技能/MCP 落地后 `setRoles(…, [新角色id])`；技能 id / MCP id 与本地冲突 → 加后缀铸新 id（沿用各自模块的 id 生成规则），并记录「包内 id → 本地 id」映射于导入结果摘要。
- 随包 MCP 导入后置 enabled=true（导出方在用的能力，开箱即用；MCP 默认关的原则对「用户显式导入」让步——导入动作本身即显式意图）。
- 知识库目录随 id 走：保留原 id 时目录名不变；铸新 id 时目录改名到新 id。

## 明确不打包

- 角色默认工作区内容（PR#49 未落地且多为项目代码）；
- ext-roles 的原始多角色分配（无法跨机保真，导入一律置为仅新角色）；
- 定时任务 / 对话绑定 / IM 回复范围（机器本地引用）。
